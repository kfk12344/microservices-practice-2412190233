## 一、项目名称

**个人健康饮食记录管理系统**（Health & Diet Tracker）

---

## 二、选题说明

### 2.1 要解决的实际问题

热量摄入与消耗的平衡是体重管理的核心，但普通人很难凭感觉判断"这一餐大概多少热量"。
现有健康类 App 普遍存在两个问题：功能繁杂（记饮食之外还要社交、打卡、商城），
以及把营养计算放在付费墙后。结果是用户记录几天就放弃，数据没有积累价值。

### 2.2 业务背景

本课题要做一个轻量、免费、数据自己掌握的健康饮食记录工具，核心只做三件事：

1. **记录得足够快** —— 一条命令或一个请求就能完成一餐记录；
2. **算得足够准** —— 营养值基于统一的食物库基准数据，口径全系统一致；
3. **看得懂** —— 当日汇总直接给出总热量与各餐次占比，不需要用户自己算。

### 2.3 主要目标用户及其需求

| 用户角色 | 核心需求 |
| :--- | :--- |
| **普通用户**（主要用户） | 快速记录三餐与加餐、查看每餐热量与营养、查看当日汇总、设定减脂/增肌目标 |
| **营养师**（可选角色） | 查看用户饮食数据、给出饮食建议、制定个性化食谱 |
| **管理员** | 维护食物库与运动库、管理用户账号、系统监控 |

### 2.4 选择该题目的原因

1. **业务边界清晰**：用户 → 记录 → 统计三层，功能模块之间耦合低，便于后续拆分服务。
2. **数据模型丰富但不复杂**：既有主数据（食物库）又有业务数据（饮食记录），
   且两者之间的关系带业务属性（份量），适合练习实体建模与关系映射。
3. **天然需要多角色**：用户 / 营养师 / 管理员三种角色，为后续"认证与权限"课程任务提供了真实场景。
4. **读写形态同时存在**：记录一餐是写事务，日报表是读聚合，两类典型问题都能覆盖。
5. **贴近生活、便于验证**：热量与营养素的计算结果可以手工核对，业务规则的对错一眼能判断。

### 2.5 项目的初步边界

**做**：饮食记录（含食物与份量明细）、食物库查询、当日热量与营养素汇总。

**不做**（至少本学期前期不做）：社交功能、商城/付费、菜品图片识别、与运动手环的硬件对接、
多端 App（先做 REST 接口，前端后置）。

### 2.6 为什么适合在后续课程中逐步演进

## 四、第 04 周：业务建模

### 4.1 本周要实现的一条核心业务流程

**记录一餐，并查看当日热量收支。**

流程描述：

1. 用户提交一餐信息：餐次（早/午/晚/加餐）、用餐时间、包含哪些食物及各自份量（克）；
2. 系统按食物库中每 100 克的营养基准值，折算本次用餐的热量、蛋白质、脂肪与碳水；
3. 系统校验业务规则（见 4.3），不合规则拒绝并说明原因；
4. 校验通过后写入数据库，并返回服务端算好的营养合计；
5. 用户查询当日汇总，系统按餐次拆分热量并给出全天合计。

这条流程同时覆盖了**写事务**（步骤 1–4）与**读聚合**（步骤 5），
也覆盖了主数据（食物库）与业务数据（饮食记录）的协作，因此选它作为第一条完整链路。

### 4.2 参与该流程的业务实体及其关系

| 实体 | 角色 | 关键属性 |
| :--- | :--- | :--- |
| **`Food`（食物库）** | 主数据，提供营养基准值 | 名称（唯一）、分类、每 100 克的热量与三大营养素 |
| **`MealRecord`（饮食记录）** | 业务主表，一次用餐 | 用餐人、餐次、用餐时间、备注 |
| **`MealItem`（饮食记录明细）** | 关联实体，记录"某餐吃了某种食物多少克" | 所属记录、食物、份量（克） |

关系：

```
MealRecord 1 ──── N MealItem N ──── 1 Food
   一条记录包含多条明细；每条明细指向一种食物并记录该次的份量
```

对应的库表关系见 [docs/database.md](database.md)。

**为什么把"份量"放在明细上**：同一种食物在不同记录里的份量不同（今天 150g 米饭、昨天 200g），
说明份量属于"记录 × 食物"这一组合，而不是食物本身的属性。
这一点也直接决定了"只靠两张表不够"——需要一张带业务字段的关联表。

### 4.3 需要在 Service 中检查的业务规则

作业要求至少 1 条。本项目在此基础上实现了 **5 条**，全部集中在
`MealRecordService`，阈值统一由 `BusinessLimits` 提供（保证接口暴露的数字与实际校验用的是同一份常量）。

| 编号 | 规则 | 阈值 | 检查位置 |
| :--- | :--- | :--- | :--- |
| **R1** | 食物必须存在于食物库；份量为正且不超过上限 | 份量 ≤ 5000 g | `MealRecordService.create` → `loadFoods()` |
| **R2** | 用餐时间必须落在所选餐次的时间窗内；且同一时间不允许重复提交同餐次记录 | 早餐 05:00–10:59<br/>午餐 11:00–14:59<br/>晚餐 17:00–21:59<br/>加餐 其余时刻 | `MealRecordService.create` |
| **R3** | 单次用餐热量不得超过上限 | 1500 kcal | `MealRecordService.create` |
| **R4** | 单次用餐最多包含若干种食物 | 10 种 | `MealRecordService.create` |
| **R5** | 同一天最多记录若干餐 | 12 餐 | `MealRecordService.create` |

其中 **R3（单餐热量上限）是本周的核心业务规则**：

- 它依赖真实的业务计算（按份量折算热量），而不是简单的字段校验；
- 阈值有明确依据：普通成年人全天推荐摄入约 1800–2400 kcal，单餐超过 1500 kcal
  基本意味着份量填错，值得拦截而不是默默记下；
- 它可被独立验证：`MealRecordServiceTest` 中有对应的边界测试，
  `MealApiIntegrationTest` 中有端到端测试（2000g 米饭 = 2320 kcal → 422）。

规则被违反时，接口返回 **422 Unprocessable Entity** 并在 `details` 中带上规则编号与说明，
便于客户端区分"格式错误"（400）与"业务冲突"（422）：

```json
{
  "status": 422,
  "code": "BUSINESS_RULE_VIOLATION",
  "message": "本次用餐热量 2320.00 kcal 超过单餐上限 1500 kcal，请调整份量或拆分为多条记录",
  "details": ["违反规则：R3 —— 单次用餐热量不得超过 1500 kcal"]
}
```
