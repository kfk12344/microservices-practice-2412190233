## 四、作业系统中需要填写的文字

### 4.1 Week 04 · 业务建模（≥50 字符）

> 本周把选题中的"记录一餐 → 折算营养 → 查看当日汇总"落地为一条完整流程。参与流程的实体有三类：`Food`（食物库，主数据，营养值统一按每 100 克存储）、`MealRecord`（饮食记录，含用餐人、餐次、用餐时间）、`MealItem`（记录明细，承载"某餐吃了某种食物多少克"）。三者关系为 `MealRecord 1—N MealItem N—1 Food`，份量之所以放在明细而不是食物上，是因为同一种食物在不同记录里份量不同，份量属于"记录 × 食物"的组合。核心业务规则是 R3：单次用餐热量不得超过 1500 kcal，依据是普通成年人全天推荐摄入约 1800–2400 kcal，单餐超过 1500 基本意味着份量填错。该规则依赖真实折算而非字段校验，并在 Service 中集中实现，共落地 5 条规则（R1–R5），阈值统一由 `BusinessLimits` 提供，保证接口暴露的数字与实际校验一致。

### 4.2 Week 04 · 单体应用实现（≥20 字符）

> 在 `monolith/` 中实现了 3 个实体、3 个 Service（`MealRecordService`、`DailySummaryService`、`FoodService`）与 2 个 Controller，共 9 个 REST 接口（业务接口 6 个，含 4 个查询与 1 个创建，路径统一 `/api/` 前缀）。Controller 只负责 HTTP 输入输出与状态码，全部数据访问经 Service 到 Repository，业务规则集中在 Service。验证方法：启动应用后依次请求 `GET /api/meals/daily-summary?eater=demo-user&date=2026-09-28` 得到当日 4 餐合计 1497.4 kcal 与分餐次拆分；再 `POST /api/meals` 提交 2000g 米饭，因热量 2320 kcal 超过单餐上限返回 422 与规则编号 R3。全部响应已存档在 `验证脚本/验证输出-接口响应.txt`。

### 4.3 Week 04 · 数据库持久化（≥20 字符）

> 接入 MySQL，共 3 张表：`food`（食物库，`name` 唯一，四项营养值非负）、`meal_record`（饮食记录，餐次受 CHECK 约束，`(eater, eaten_at)` 建复合索引）、`meal_item`（明细，`(meal_record_id, food_id)` 唯一约束保证同餐同食物只有一行，外键级联删除，份量为正）。数据访问使用 Spring Data JPA 并集中在 `repository` 包，API 输入由 `dto` 包的请求对象承载。表结构由 `schema.sql` 统一负责（JPA 侧 `ddl-auto: none`），与 `data.sql` 一起写成幂等语句，可重复执行。验证方法：执行 `mysql -u root -p health_diet < schema.sql` 与 `data.sql` 后启动应用，`GET /api/foods` 返回 12 条食物、`GET /api/meals?eater=demo-user` 返回 4 条记录；测试环境改用 H2，`./mvnw test` 同样加载这两个脚本。

### 4.4 Week 04 · 测试与验证（≥20 字符）

> 三类验证各有覆盖：Repository 读写由 `MealRecordRepositoryTest`（9 个）验证，含份量往返一致性与级联删除；Service 业务规则由 `MealRecordServiceTest`（11 个）用 Mockito 隔离数据层，逐条覆盖 R1–R5 及边界；API 正常与错误响应由 `MealControllerTest`（11 个，MockMvc）与 `MealApiIntegrationTest`（12 个，`TestRestTemplate` 真实 HTTP）覆盖 200/201/400/404/422。测试使用 H2 内存库（MySQL 兼容模式）并加载生产用的 `schema.sql` 与 `data.sql`，因此在 `monolith/` 下执行 `./mvnw test` 无需本机安装 MySQL，结果为 Tests run: 75, Failures: 0, Errors: 0, Skipped: 0 — BUILD SUCCESS。
